## What arrives, versus what you assumed arrived

Here is a five-row table of student records, the kind an office produces when several people maintain a spreadsheet over two years.

```
        student        city         marks      joined
0    Ravi Kumar   Hyderabad            78  01/02/2023
1    ravi kumar   hyderabad            82  2023-02-03
2      Priya S.   Bengaluru  not recorded  15/03/2023
3      ANJALI R   Bangalore            91  2023-03-20
4      Priya S.   Bengaluru            88  15/03/2023
```

Five rows and at least six distinct problems. Every one of them is ordinary, and every one produces a wrong answer rather than an error.

## What is actually wrong here

| Problem | Where | What it breaks |
| ------------------------ | -------------------------------- | ---------------------------------------- |
| Inconsistent case | `Ravi Kumar` and `ravi kumar` | Counts, grouping, joins |
| Trailing whitespace | `hyderabad ` | The same, invisibly |
| Two names for one thing | `Bengaluru` and `Bangalore` | Splits one city into two |
| Text in a numeric column | `not recorded` in marks | All arithmetic on the column |
| Mixed date formats | day-first and ISO in one column | Date parsing, ordering, filtering |
| Probable duplicate row | Priya appears twice | Every count and every average |

The marks column shows the cost immediately:

```python
raw['marks'].mean()
```

```
TypeError: Cannot perform reduction 'mean' with string dtype
```

One value out of five turned the entire column into text. This is the most common reason a numeric column arrives unusable, and it is why checking `dtypes` after loading is not optional.

## The categories these fall into

Six kinds of problem cover almost everything you will meet.

Missing values, whether blank, coded as 999, or spelled out as "not recorded". Duplicates, whether exact or near. Wrong types, usually numbers stored as text. Inconsistent categories, where one thing has several spellings. Structural problems, such as merged header rows or a total row at the bottom. And impossible values, which are the outliers from the earlier unit.

Only some of these announce themselves. The marks column raised an error, which is the friendly case. The city column will quietly report two cities where there is one, and nothing will ever object.

> The dangerous problems are the ones that produce plausible output. An error stops you; a silently split category lets you publish.

## Why the order of cleaning matters

These problems interact, and fixing them in the wrong order produces wrong answers.

Consider duplicates. In the table above, `duplicated()` on student and city finds one repeat: the two Priya rows match exactly. Standardise the names first, so `ravi kumar` becomes `Ravi Kumar` and `hyderabad ` becomes `Hyderabad`, and the count rises to two.

```
duplicates before cleaning: 1
duplicates after cleaning:  2
```

The Ravi rows were always duplicates. The difference in capitalisation hid it, and a deduplication run before standardisation would have kept both.

The general rule follows from that: standardise text before grouping, counting, joining, or deduplicating. Anything that compares values needs the values to be comparable first.

## A working order

| Step | Why it comes here |
| ---------------------------- | ----------------------------------------- |
| 1. Inspect and record the state | You cannot check a fix without a baseline |
| 2. Fix structure | Headers, stray rows, wrong shape |
| 3. Fix types | Later steps depend on columns being what they claim |
| 4. Standardise text | Everything comparing values needs this first |
| 5. Handle duplicates | Now that matches are visible |
| 6. Handle missing values | Once you know what missing means here |
| 7. Check impossible values | Against ranges that now parse correctly |

The first step is the one people skip. Record the row count, the missing counts, and the distinct values per category column before touching anything, because that is what you compare against afterwards to confirm your cleaning did what you intended and nothing else.

## Clean for the question, not for tidiness

Cleaning can absorb an entire project. Some of it is necessary and some is decoration.

A column you will never use does not need standardising. A category with three spellings matters enormously if you are grouping by it and not at all if you are ignoring it. The measure of a cleaning step is whether an analysis you actually plan to run depends on it.

What does deserve unconditional effort is recording what you did. Every decision to drop rows, recode a category, or fill a gap changes the results, and a reader who cannot see those decisions cannot judge the findings.

## Practise the inventory

Take a messy file, preferably from a public portal.

Before fixing anything, write a numbered list of every problem you can find, one line each, with the column it affects and what it would break. Aim for at least six.

Then decide which of them your intended analysis actually depends on, and mark the rest as noted but not fixed. That distinction is what keeps cleaning from becoming the whole project.
