## When the values that should match do not

A merge with correct syntax and a sensible join type can still return nothing at all.

```python
import pandas as pd
df = pd.read_csv('penguins.csv')

bad = pd.DataFrame({'species': [' adelie', 'GENTOO'],
                    'diet': ['krill', 'fish']})

len(df.merge(bad, on='species', how='inner'))      # 0
```

Zero rows. Both tables contain Adelies and Gentoos, and not one row matched.

The keys are ` adelie` with a leading space and lowercase, against `Adelie` in the data. Matching is exact, so these are different values.

## After cleaning

```python
bad['species_clean'] = bad['species'].str.strip().str.title()
len(df.merge(bad, left_on='species', right_on='species_clean', how='inner'))      # 276
```

Two string operations turned zero matches into 276.

This is the concrete argument for the standardisation habit from the cleaning unit. Whitespace and case are invisible on screen and decisive to every join.

## The usual causes

| Cause | Looks like | Fix |
| ------------------------ | ------------------------------- | ------------------------------- |
| Leading or trailing spaces | Identical on screen | `.str.strip()` |
| Case differences | `Gentoo` against `GENTOO` | `.str.lower()` on both sides |
| One side numeric, one text | `101` against `'101'` | Convert one with `astype` |
| Leading zeros lost | `06821` became `6821` | Read the column as text |
| Different names for one thing | `Bengaluru` against `Bangalore` | An explicit mapping |
| Trailing punctuation | `Ltd.` against `Ltd` | `.str.replace()` |

The type mismatch is the one that catches experienced people. A key read as an integer from one file and as text from another will never match, and the printed values look identical.

## Finding the mismatches

When a merge under-matches, the question is which keys failed. Set operations answer it directly:

```python
left_keys = set(df['species'])
right_keys = set(bad['species'])

left_keys - right_keys      # in the data, absent from the lookup
right_keys - left_keys      # in the lookup, absent from the data
```

Reading both differences usually identifies the problem in seconds. Values differing only by case or spacing appear in both sets, which is the signature of a formatting issue rather than a missing entry.

> Before debugging a merge, print the unmatched keys from both sides. The pattern in that list tells you whether you have a cleaning problem, a coverage problem, or the wrong key entirely.

## A cleaning routine for keys

Apply the same treatment to both sides before merging, and keep it in one place so it cannot drift:

```python
def clean_key(s):
    return s.str.strip().str.lower()

left['key'] = clean_key(left['raw_key'])
right['key'] = clean_key(right['raw_key'])
```

Defining it as a function matters more than what is inside it. The failure mode is stripping one side and not the other, and a shared function makes that impossible.

## Duplicate keys after cleaning

Standardising can create duplicates that were not visible before. If a lookup contains `Adelie` and `adelie` as separate rows, they were distinct keys and become one after lowercasing, and now the lookup has a duplicate.

Check for duplicates after cleaning rather than before, and use `validate` on the merge itself so the check happens where it matters.

## When keys are only approximately equal

Some mismatches survive every mechanical fix. `Ravi Kumar` and `Ravi Kumar.`, a company recorded with and without its legal suffix, an address written two ways.

Fuzzy matching compares how similar two strings are and accepts a match above a threshold. It is a substantial topic and it introduces a new risk, since a threshold low enough to catch real matches is usually low enough to create false ones.

The practical position for now: standardise mechanically, list what remains unmatched, and handle the residue by hand if it is small. A list of forty unmatched keys is an afternoon; a fuzzy match run without review is a permanent uncertainty in your data.

## Practise the diagnosis

Take two tables that should join and deliberately corrupt one side's key: add whitespace to some values, uppercase others, and convert the column to text.

Merge and observe the row count collapse. Then use the two set differences to identify which keys failed and why.

Then write a single cleaning function, apply it to both sides, and confirm the count returns. That sequence is the one you will repeat every time a join disappoints you, which is often.
