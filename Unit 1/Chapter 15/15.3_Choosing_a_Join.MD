## Row loss, row multiplication, and neither raising an error

A merge that runs without complaint can still be wrong in two directions. It can quietly discard rows, and it can quietly create rows that did not exist.

Both are invisible unless you count.

## Rows disappearing

```python
import pandas as pd
df = pd.read_csv('penguins.csv')
partial = pd.DataFrame({'species': ['Adelie', 'Gentoo'], 'diet': ['krill', 'fish']})

len(df.merge(partial, on='species', how='inner'))      # 276
len(df)                                                # 344
```

Sixty-eight birds vanished. Every Chinstrap, because the lookup table did not mention them.

Nothing about the result signals this. It is a well-formed DataFrame with 276 rows, and every subsequent summary is computed on a file missing one of its three species.

## Rows multiplying

The opposite failure is less familiar and more damaging.

```python
dup = pd.DataFrame({'species': ['Adelie', 'Adelie', 'Gentoo'],
                    'note': ['n1', 'n2', 'n3']})

len(df.merge(dup, on='species', how='left'))      # 496
```

344 rows became 496. The lookup contains Adelie twice, so every Adelie penguin matched both rows and appeared twice in the output.

```
Adelie: 304    Gentoo: 124    Chinstrap: 68
```

There are 152 Adelies in the file and 304 in the result. Every count, sum, and average involving Adelies is now doubled, and the table looks perfectly normal.

> A merge that increases your row count has duplicated data. Unless you intended a one-to-many join, that is a bug, and the only thing that reveals it is comparing the count before and after.

## What causes duplicate keys

The lookup was supposed to have one row per species and had two for one of them. In real work this happens constantly.

A reference table maintained by hand accumulates a second entry after a correction. A table that records history has one row per version rather than one per entity. A key you assumed was unique, such as a customer name, is not.

The fix is to check the lookup before merging:

```python
lookup['species'].duplicated().sum()      # should be 0 for a one-to-one lookup
```

Or to let pandas check for you.

## validate stops it happening

```python
df.merge(dup, on='species', how='left', validate='m:1')
```

```
MergeError: Merge keys are not unique in right dataset; not a many-to-one merge
```

The `validate` parameter states what relationship you expect, and the merge fails if the data disagrees.

| Value | Means |
| ------- | ------------------------------------------------ |
| `'1:1'` | Keys unique on both sides |
| `'m:1'` | Many rows on the left, one per key on the right |
| `'1:m'` | One per key on the left, many on the right |
| `'m:m'` | No constraint, the default behaviour |

`m:1` is the common case: many records joining to one lookup entry. Stating it turns a silent duplication into an immediate error, which is exactly the trade you want.

Adding `validate` to every merge you write costs six characters and catches the failure that is hardest to notice afterwards.

## Choosing the join type by intent

| Your intent | Join | Then check |
| --------------------------------------------- | ------- | ---------------------------- |
| Add information, keep all my rows | `left` | Gaps in the new columns |
| Only rows present in both are meaningful | `inner` | How many rows you lost |
| Combine two partial sources of the same thing | `outer` | Gaps on both sides |
| Look up from the perspective of the other table | `right` | Rarely needed, prefer swapping the tables |

`right` is included for completeness. Swapping the two tables and using `left` does the same thing and is easier to read.

## The three checks that make a merge safe

Every merge deserves the same three lines.

```python
before = len(left)
merged = left.merge(right, on=key, how='left', validate='m:1', indicator=True)
merged['_merge'].value_counts()
len(merged) == before
```

Count before, state the expected relationship, and read the indicator afterwards. Together they catch loss, duplication, and unmatched keys.

If the row count changed on a left join, something in the right table has duplicate keys. If `left_only` is large, the keys do not match, which is the subject of the next topic.

## Practise both failures

Take a dataset and build two lookup tables: one missing some key values, one containing a duplicated key.

Merge with each and record the row count. One result should shrink, the other should grow.

Then add `validate='m:1'` and confirm the second merge now raises rather than silently duplicating. Producing both failures deliberately, once, is what makes the count check feel necessary rather than pedantic.
