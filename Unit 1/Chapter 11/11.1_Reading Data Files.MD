## Getting a file in, when the file does not cooperate

A well-formed CSV loads in one line.

```python
import pandas as pd
df = pd.read_csv('penguins.csv')
```

Real files are frequently not well formed. Here is one exported from a system in Europe:

```
# exported 2009-01-01
id;name;mass;when
1;Adelie;3.750,5;01/02/2009
2;Gentoo;5.000,0;03/02/2009
3;Chinstrap;NA;05/02/2009
```

Loading it with the default call:

```python
pd.read_csv('messy.csv')
```

```
ParserError: Error tokenizing data. C error: Expected 1 fields in line 3, saw 2
```

Four separate things are wrong: a comment line above the header, semicolons instead of commas, European number formatting where the comma is the decimal point, and day-first dates. Each has a parameter.

## The parameters that solve most problems

```python
m = pd.read_csv('messy.csv',
                sep=';',              # semicolon separated
                skiprows=1,           # drop the export comment above the header
                decimal=',',          # 3.750,5 means three thousand seven hundred fifty point five
                thousands='.',
                parse_dates=['when'],
                dayfirst=True,        # 01/02/2009 is 1 February, not 2 January
                na_values=['NA'])
```

```
   id       name    mass       when
0   1     Adelie  3750.5 2009-02-01
1   2     Gentoo  5000.0 2009-02-03
2   3  Chinstrap     NaN 2009-02-05
```

```
id               int64
name               str
mass           float64
when    datetime64[us]
```

Every column now has the right type, the missing value is recognised as missing, and the dates are dates rather than text.

The `dayfirst` parameter deserves particular attention. Indian and European files write dates as day/month/year while American files write month/day/year, and 01/02/2009 is a valid date under both readings. Nothing in the file says which, and getting it wrong shifts your data by months without any error appearing.

## The parameters worth knowing

| Parameter | What it does |
| ------------ | ------------------------------------------------- |
| `sep` | The delimiter, when it is not a comma |
| `header` | Which row holds column names, or `None` for none |
| `skiprows` | Lines to ignore before the header |
| `names` | Supply column names yourself |
| `usecols` | Read only some columns |
| `nrows` | Read only the first few rows |
| `dtype` | Force a column's type |
| `na_values` | Extra strings that mean missing |
| `parse_dates` | Columns to convert to dates |
| `encoding` | The text encoding, when the default fails |

## Reading part of a large file first

```python
pd.read_csv('penguins.csv', usecols=['species', 'body_mass_g'], nrows=3)
```

```
  species  body_mass_g
0  Adelie         3750
1  Adelie         3800
2  Adelie         3250
```

On a file of several gigabytes, loading three rows and two columns takes a moment and tells you the structure. Do this before the full load, always.

Note the dtype here: with only the first three rows, none of which is missing, `body_mass_g` came in as an integer. Read the whole file and it becomes a float, because two rows have gaps. A type inferred from a sample is a guess about the rest.

## Forcing a type

```python
pd.read_csv('penguins.csv', dtype={'year': 'str'})
```

Sometimes a numeric-looking column should be text. Pin codes, phone numbers, employee IDs, and anything with leading zeros all lose information when read as numbers, since 06821 becomes 6821.

Passing `dtype` at read time is the fix, and it is easier than repairing the column afterwards.

> Whenever a column is an identifier rather than a quantity, read it as text. You will never do arithmetic on it, and you will lose leading zeros if you do not.

## Encoding failures

A `UnicodeDecodeError` on load means the file's text encoding is not what pandas assumed. Files exported from older Windows software are often `latin-1` or `cp1252` rather than UTF-8.

```python
pd.read_csv('file.csv', encoding='latin-1')
```

That usually resolves it. If the file mixes encodings, which happens, `encoding_errors='replace'` will load it with unreadable characters substituted, which is a compromise worth making only after you have looked at what is being replaced.

## Other formats

| Function | Reads |
| -------------- | ---------------------------------- |
| `read_excel` | `.xlsx` and `.xls`, with `sheet_name` |
| `read_json` | JSON, flat or nested |
| `read_parquet` | Columnar format, fast and typed |
| `read_sql` | A query against a database |
| `read_html` | Tables from a web page |

`read_excel` needs an extra package installed and is considerably slower than `read_csv`. For a file you will load repeatedly, converting once to CSV or Parquet is worth the trouble.

## Practise on a file that fights you

Find a CSV from a government portal rather than a teaching repository.

Load it with the plain call and note what breaks. Then fix it one parameter at a time, checking `dtypes` after each step.

Then load only the first ten rows and compare the inferred types against those from the full file. Where they differ, you have found a column whose contents change partway through, which is one of the most common surprises in real data.
