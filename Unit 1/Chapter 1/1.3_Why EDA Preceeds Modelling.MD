## A tool will not tell you that the data is wrong

Type your friends' phone numbers into a spreadsheet column and ask for the average. You will get one. The spreadsheet has no idea the column is not a quantity, and it will never raise the question.

Every data tool behaves this way. It checks whether a calculation is possible, never whether it is meaningful.

A final-year team learns this the hard way. They build something to predict which students will be placed, using a file of 4,000 student records and about thirty columns. The predictions come out correct almost every time, and the team is delighted for roughly a day.

Then someone scrolls through the file. One column is `offer_date`. It holds a date for every placed student and a blank for everyone else, because the placement office fills it in after a student receives an offer. The prediction was not predicting. It was reading the answer off the page.

That column was visible in row one. Nobody looked, because looking felt like the boring part.

## What no technique can notice for you

A technique consumes columns as values and returns an output. It cannot know what a column means, when it was filled in, or whether it belongs in the file at all.

| What sits in the file | What it actually means | What happens if nobody looks |
| ------------------------------------ | -------------------------------------------- | ------------------------------------------- |
| A column filled only for one group | It was recorded after the outcome was known | The result looks near-perfect and is worthless |
| `9999` in an age column | A code the form uses for "not provided" | Every summary of age is dragged upward |
| A block of identical rows | The same sheet was uploaded twice | Those people count twice in every comparison |
| A category retired last year | The data describes a rule no longer in force | The finding cannot be acted on |
| A column with one value in every row | The field was added but never filled | Time spent analysing something that says nothing |
| `Bangalore`, `bangalore`, `Bengaluru` | One city recorded three ways | The city gets split into three smaller ones |

Each of these is caught by scrolling, counting, and asking one question about a column. None is caught by applying something more sophisticated afterwards.

> Confidence is produced by the technique. Correctness is produced by you, earlier.

## The checks that catch most of it

The first look at a dataset is not a vague act of familiarisation. It is a short list of questions with checkable answers, and it takes minutes.

| The check | What you are looking for |
| ------------------------------ | ------------------------------------------------- |
| How many rows and columns? | A number that matches what you were told to expect |
| What does each column mean? | Any column you cannot explain in one sentence |
| Where are the blanks? | Columns that are mostly empty, and rows that are entirely empty |
| What are the distinct values? | Spelling variants, stray codes, categories you did not expect |
| What is the date range? | Data that stops early, or starts before the system existed |
| Are any rows duplicated? | Repeated uploads and merge accidents |

Run those six on the placement file and `offer_date` fails the second check immediately. Nobody on the team could have explained, in one sentence, when that field gets filled in, and that discomfort is the signal.

## The same mistake gets dearer the longer it lives

* Caught while looking around: a few minutes, and you learn something about how the data was recorded.
* Caught after the analysis is built: days of rework, and every earlier result is now in doubt.
* Caught after somebody acted: a scholarship goes to the wrong students, and fixing the file does not undo it.

The third case is the reason this ordering exists at all. Analysis produces confident output regardless of what went in, and confidence is exactly what makes people act on it.

There is a second cost that is easy to miss. Errors found late damage trust in everything else you produced, including the parts that were correct. A team that has to withdraw one number is usually asked to justify all of them.

## What looking first cannot promise

Exploration finds problems that are visible in the file you hold, and only those.

It cannot find the students who were never entered into the system. It cannot tell you that the attendance column was filled in each Friday from memory rather than recorded in class. It cannot reveal that one department stopped reporting in March and nobody noticed. Those flaws leave no trace in the numbers, and only asking the people who collected the data will surface them.

That is why the six checks above end where they do. After the file has told you everything it can, the next questions go to a person.

There is an opposite failure too. A dataset can be examined indefinitely, and there is always one more column with an oddity in it. When you cannot say which decision a check supports, that check is probably optional.

## Which of these would a technique catch on its own?

| Problem in the data | Caught automatically? | Why |
| ------------------------------------------------- | --------------------- | ------------------------------- |
| A text value sitting in a numeric column | Usually yes | The operation fails loudly |
| `9999` standing in for a missing age | No | It is a valid number |
| A column that could only be filled after the outcome | No | It makes the result look better |
| Two spellings of the same city | No | Both are valid text values |
| A file with half the rows missing entirely | No | Nothing compares it to what should be there |

The first row stops your program. The other four do not, and they are the ones that cost something.

## The bar to clear, and how to practise it

Before you build anything on a dataset, you should be able to say what each column you plan to use means, who filled it in and when, what its blanks and odd values stand for, and whether the rows you have are the rows you think you have.

That is a low bar and most files fail it.

Practise on any dataset you can download. Pick five columns and write one sentence for each explaining what it holds and when it gets filled in. You will manage three comfortably and stall on two, and those two are exactly where the file will surprise you later.

The team with the near-perfect placement predictor had built something impressive and could not answer a single one of those questions, which is the only reason anyone noticed in time.
