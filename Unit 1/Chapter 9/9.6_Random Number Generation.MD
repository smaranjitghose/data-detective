## Generating data you can reproduce

Randomness turns up throughout analysis: drawing a sample, shuffling rows, simulating a process to see how a statistic behaves, splitting data into two halves.

```python
import numpy as np
rng = np.random.default_rng(42)
rng.random(3)        # [0.774  0.4389 0.8586]
```

Run that again in a fresh session and you get the same three numbers. The 42 is a seed, and it makes the sequence reproducible.

```python
rng = np.random.default_rng(42)
rng.random(3)        # [0.774  0.4389 0.8586]  again
```

## Why the seed is not optional

An analysis involving randomness that gives a different answer every run cannot be checked by anyone, including you.

Someone reading your work needs to reproduce your numbers. A reviewer questioning a result needs to see the same output. You, three weeks later, need to know whether a changed result came from your edits or from the dice.

Set a seed at the top of any notebook using randomness. Any value works; the convention of 42 exists only because it is memorable.

> Reproducibility is not a nicety in work involving randomness. Without a seed, your result is an anecdote rather than a finding.

## The generator interface

Modern NumPy creates a generator object and calls methods on it.

```python
rng = np.random.default_rng(7)

rng.integers(1, 7, size=10)          # [6 4 5 6 4 5 6 2 1 2]
rng.normal(60, 10, size=5)           # [50.08 60.6  73.4  55.08 53.8 ]
rng.choice(np.arange(100), 5, replace=False)   # [33 78 71 27 29]
```

You may see older code calling `np.random.seed()` and `np.random.rand()` directly. That interface still works and is no longer recommended, because it uses one shared global state that any library can disturb. A generator you create belongs to your code.

| Method | Produces |
| --------------- | ------------------------------------------- |
| `random(n)` | `n` values uniformly between 0 and 1 |
| `integers(low, high, size)` | Whole numbers, `high` excluded |
| `normal(mean, sd, size)` | Values from a normal distribution |
| `choice(a, size, replace)` | A sample drawn from an existing array |
| `shuffle(a)` | Reorders an array in place |
| `permutation(a)` | A shuffled copy |

Note the exclusive upper bound on `integers`. Simulating a die needs `rng.integers(1, 7)`, not `(1, 6)`, which is a bug worth catching in advance.

## Sampling with and without replacement

`replace=False` draws each element at most once, which is what sampling from a population means. `replace=True` allows repeats, which is what you want when simulating repeated independent draws.

Getting this backwards produces a sample containing the same row three times, and nothing about the output announces it.

## Simulation as a way of checking your reasoning

Random generation is not only for making test data. It is a way of answering probability questions you are unsure about.

```python
rng = np.random.default_rng(0)
rolls = rng.integers(1, 7, size=100_000)
rolls.mean()          # 3.498
```

The theoretical mean of a fair die is 3.5, and a hundred thousand simulated rolls gave 3.498. When a probability argument is hard to follow, simulating it and checking the answer is faster than re-reading the derivation, and it catches mistakes in your reasoning that algebra hides.

This is the same technique behind the sampling demonstration in the probability unit, where repeatedly drawing samples showed the spread of sample means shrinking with the square root of the sample size.

## Where randomness enters real work

Four places, and each needs a seed.

Splitting data into parts, whether for checking a finding on a portion you did not explore or for any other reason. Drawing a sample from a file too large to work with whole. Shuffling before splitting, because files often arrive sorted in ways that would make an unshuffled split badly unrepresentative. And simulating a process to understand how much a result might vary.

That third one is easy to forget. A dataset ordered by date, split without shuffling, gives you the first months in one part and the last months in the other, which is rarely what you intended.

## Practise the reproducibility

Generate ten random numbers with a seed. Restart your kernel entirely and generate them again.

Then generate ten without a seed, restart, and generate again. Compare.

Then simulate something you know the answer to: the mean of a die, the proportion of heads in a coin toss, or the average of a normal distribution you specified. Checking that the simulation returns the value you expected is how you build confidence in the ones where you do not know the answer in advance.
