## Two kinds of cells, two modes, and about ten keys

Watch a beginner work in a notebook and the mouse travels to the toolbar for every action. Watch someone experienced and their hands barely leave the keyboard. The difference is not talent. It is about ten shortcuts, learned once.

Before the shortcuts, two ideas have to be clear, because every confusing moment in a notebook traces back to one of them.

## Code cells and text cells

A notebook holds cells of two useful kinds. A code cell contains Python and produces output when run. A markdown cell contains formatted text and renders into a neat paragraph when run.

Running a text cell feels odd at first. You are not executing anything; you are asking the notebook to render the formatting. The same keys as for code turn raw text into a heading or a bulleted list.

A third type, raw, exists for export purposes and you can ignore it for now.

## Command mode and edit mode

A cell is either selected or being typed in, and the keyboard means different things in each state.

In edit mode, with a cursor blinking inside the cell, keys type characters. Press Escape and you leave for command mode, where the cell has a coloured border and single keys become commands. Press Enter to go back in.

Most frustration with shortcuts comes from firing them in the wrong mode. Pressing `b` in command mode makes a new cell below. Pressing `b` in edit mode types the letter b.

| Key | Mode | What it does |
| ------------- | ------- | ---------------------------------- |
| `Esc` | Edit | Leave the cell, enter command mode |
| `Enter` | Command | Start typing in the selected cell |
| `Shift+Enter` | Either | Run the cell and select the next |
| `Ctrl+Enter` | Either | Run the cell and stay on it |
| `a` / `b` | Command | Insert a cell above / below |
| `dd` | Command | Delete the selected cell |
| `m` / `y` | Command | Convert to markdown / to code |
| `z` | Command | Undo the last cell operation |
| `Shift+M` | Command | Merge selected cells |
| `Ctrl+Shift+-` | Edit | Split the cell at the cursor |

Learn `Shift+Enter`, `Esc`, `a`, `b`, and `m` first. Those five cover most of a working session. The last two in the table matter once your cells start growing past a screen, which they will.

## Magic commands

Jupyter adds commands that are not Python. They start with a percent sign and are called magics, and a handful earn their place early.

```python
%pwd                    # which folder this notebook is running in
%ls                     # what files are next to it
%time  expensive_call()  # how long one statement took
```

```python
%%time
# a whole cell timed, because the double percent applies to the cell
total = sum(range(10_000_000))
```

One percent sign applies to a single line, two apply to the whole cell. A related trick uses an exclamation mark to run a shell command, which is how people install a package without leaving the notebook:

```python
!pip install pandas
```

Use that sparingly. A notebook that installs things when it runs is a notebook that behaves differently on someone else's machine, and `%pwd` is far more useful day to day than any of the rest, because it answers the single most common beginner question: why can it not find my file.

## The numbers beside your cells are telling you something

Every executed code cell gets a number in brackets: `[1]`, `[2]`, and so on. That number is the order in which cells ran, not their position on the page.

This is the most useful diagnostic in a notebook. Read the numbers down the page. If they run 1, 2, 5, 3, 9, your notebook was not executed in the order it now reads, and the results on screen may not be reproducible by anyone reading it top to bottom.

| What you see | What it means | What to do |
| ------------ | -------------------------------------- | ------------------------------- |
| `[ ]` | Never run in this session | Run it |
| `[*]` | Currently running, or queued behind something | Wait, then interrupt if stuck |
| `[7]` after `[12]` | Cells ran out of order | Restart and run all |
| Numbers restart at 1 | The kernel was restarted | Expected, not a problem |

Interrupting and restarting are different actions. Interrupt stops the current cell and keeps your variables. Restart discards everything in memory. Reach for interrupt first when a cell hangs, and restart when the state itself has become the problem.

> The order you ran things in and the order they appear in are different things, and only one of them is visible to your reader.

## The habit that prevents the most embarrassment

A notebook that works on your screen has proved almost nothing. It has proved that some sequence of executions, in some order, using variables that may no longer appear in any visible cell, produced this output.

The check is Restart Kernel and Run All Cells, from the Kernel menu. It throws away all memory and runs every cell from the top in the order they appear. If the notebook survives that, it is reproducible.

Run it before you share a notebook, before you submit one, and before you trust a result you plan to act on. Doing it early is cheap. Doing it after the numbers have gone into a report is how people discover their analysis does not run.

## Build one deliberately

Open a notebook and construct a small one on purpose. Put a heading in a markdown cell, an import in a code cell, and a calculation in another. Use `Esc` then `b` to add cells rather than the toolbar, and `m` to convert one to text.

Then break it on purpose. Run cells out of order and watch the numbers jump. Define a variable, delete the cell that defined it, and confirm that later cells still work. Finally restart and run all, and watch it fail.

Ten minutes of this makes the notebook feel like an instrument rather than a webpage, and every one of those failures is one you will otherwise meet for the first time under deadline.
