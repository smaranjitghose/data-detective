## Write down why, while you still remember why

Open a notebook you wrote three weeks ago. The code runs. The charts appear. And you cannot remember why you dropped those rows, what that threshold was based on, or which of two versions of the number you eventually believed.

The code recorded every step you took and none of the reasons you took them. Reasons live in markdown cells, and they are the difference between a notebook that documents an analysis and one that merely performed it.

## The syntax, which is small

A markdown cell holds formatted text. Type into it, run it, and the raw text renders.

| You type | You get |
| ------------------- | ---------------------- |
| `## Heading` | A section heading |
| `**important**` | Bold text |
| `*emphasis*` | Italic text |
| `- item` | A bulleted list |
| `1. item` | A numbered list |
| `` `df.head()` `` | Inline code formatting |
| `> note` | An indented quote block |
| `[label](url)` | A link |

Three backticks open and close a block of code inside a text cell, which is useful for showing a command you are not running.

Headings do work beyond appearance. Jupyter builds a table of contents from them and lets you collapse sections, so a long notebook with headings stays navigable and one without them becomes a scroll.

## What is worth writing down

The instinct is to describe what the next cell does. Resist it. The code already says what it does, and an English translation goes stale the moment the code changes.

Four things earn the keystrokes:

* The question this section answers, stated before the code that answers it.
* Why a decision went the way it did, especially a decision to exclude something.
* What an output means, written immediately after you read it.
* What you have not checked, so a reader knows the edge of your confidence.

The third is the highest-value habit here. You read a result, understand it for about ninety seconds, and move on. One sentence written in that window captures an understanding that is otherwise gone by tomorrow.

> The code is what you did. The markdown is what you learned. Only one of those is hard to reconstruct later.

## The difference in practice

Two markdown cells written above the same code.

The first: *Now we drop the null values and convert the date column.*

The second: *Twelve rows have no recorded collection date. All twelve are from Zone 4 in March, when the office changed systems, so they are missing for a known reason rather than at random. Dropping them makes Zone 4's March figure unreliable and leaves everything else intact.*

The first repeats the code. The second tells a reader something the code cannot: how many rows, where from, why, and what the decision costs. It also tells future-you not to quote Zone 4's March number in the summary, which is exactly the sort of thing you will otherwise forget.

## A structure that suits an analysis

Notebooks read best when they open with the question and close with the answer, with the working in between.

| Position | What goes there |
| -------------- | ------------------------------------------------------- |
| First cell | The question, the data source, and the date |
| Section headings | One per stage, naming what you are about to ask |
| After each output | One sentence on what came back |
| Last section | The finding, its size, and what it does not cover |

That final section takes five minutes and is the part anyone senior actually reads. Writing it forces you to notice when you do not have a finding yet.

Documentation written at the end is fiction. You will describe the tidy path you wish you had taken rather than the messy one you did, and the dead ends, which are the parts most useful to the next person, vanish entirely. Write as you go, roughly, and clean up later.

## What not to put in a notebook

Two cautions worth stating plainly.

Anything secret does not belong in a cell. Database passwords and API keys typed into a notebook end up in the saved file, which then gets emailed, committed, and shared.

And personal data about identifiable people should not sit in a notebook that travels. Notebooks store their output, so a table of names printed once in cell 12 stays in the file forever, long after you have stopped thinking about that cell.

## Test it on someone

Hand your notebook to a classmate who knows Python but not your dataset, and ask them to read it without running anything.

If they can say what question you asked, what you decided along the way, and what you concluded, the documentation is working. If they have to read your code to work out your intentions, the reasoning never made it out of your head.

Try this once on the notebook you consider your best. Most people find the gap is not in their code at all, and the fix takes twenty minutes.
