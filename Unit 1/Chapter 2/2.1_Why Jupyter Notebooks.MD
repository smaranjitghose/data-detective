## Exploration needs a tool that remembers what you just did

Write a Python script that loads a large file, does something to it, and prints a result. Now change one line and run it again. Everything happens from the beginning, including the slow file load. Change another line, wait again.

That loop is fine when you know what you are building. It is painful when you are finding out, and finding out is the whole job here. A first look at a dataset means asking twenty small questions in an hour, most of them prompted by the answer to the last one.

A notebook fixes this by splitting your work into cells that run separately, while results stay alive in memory between them. Load the file once in the first cell. Every question after that runs against data already in memory, and takes as long as the question deserves rather than as long as the file does.

## What exploration needs, and what a notebook gives it

| What the work needs | What a notebook does about it |
| ------------------------------------------ | ------------------------------------------------ |
| Ask one small question at a time | Each cell runs on its own |
| Not reloading data for every question | The kernel keeps everything in memory between cells |
| See the answer next to the question | Output appears directly under the cell that made it |
| Record why you did something | Text cells sit between code cells |
| Hand the whole thing to someone else | Code, output, and reasoning travel in one file |

The last two matter more than beginners expect. An analysis is not just the code that produced a number. It is the reasoning behind the number, and a notebook is one of the few formats carrying both.

> A script says what to do. A notebook says what you asked, what came back, and what you concluded.

## The kernel is the thing actually doing the work

When a notebook opens, a separate process starts behind it. That process is the kernel, and it holds every variable you have created. The notebook in your browser is a document; the kernel is the running Python session underneath.

This one idea explains most of the confusing behaviour you will meet.

| What you observe | What is happening underneath |
| ----------------------------------------------- | ---------------------------------------------- |
| A variable from a deleted cell still works | The kernel holds values, not cells |
| A file loaded ten minutes ago is still loaded | Nothing is discarded until you say so |
| Your notebook works, a friend's copy fails | Their kernel never ran your earlier versions |
| A cell hangs with `[*]` beside it | The kernel is busy and will not run anything else |
| Restarting fixes an inexplicable error | The error lived in memory, not in your code |

Because state survives, a notebook can work perfectly for you and fail for everyone else. You created a variable in a cell, edited that cell into something different, and never re-ran it. Your kernel remembers the old version. A fresh kernel will not.

## How output appears, and what that lets you do

Two things produce visible output in a code cell, and knowing the difference saves a lot of clutter.

Anything you `print` is shown. Separately, the value of the last expression in a cell is displayed automatically, which is why a cell ending in a variable name shows that variable without any print at all.

```python
x = 5 * 12
x          # displayed automatically, because it is the last expression
```

```python
print("checking")   # printed
y = 5 * 12          # nothing displayed, this is an assignment
```

This is why analysts end cells with the thing they want to look at. It also explains a common surprise: put two expressions on separate lines and only the last one appears, because only the last one is the cell's value.

## Notebooks are a format, not a single application

The `.ipynb` format is open, which is why the same notebook opens in several places. Which one you use changes the interface and nothing about the ideas above.

| Where | What it suits |
| --------------- | ------------------------------------------ |
| JupyterLab | Local work on your own machine, full file browser |
| Classic Notebook | The older, lighter interface, still common |
| VS Code | People already living in that editor |
| Google Colab | No installation, free compute, easy sharing |

Colab deserves a mention for a practical reason: it needs nothing installed and runs in a browser, which makes it the fastest way to start if your own setup is fighting you. The kernel behaviour is identical, including everything above about state.

## Where notebooks came from

Jupyter grew out of IPython, an enhanced interactive Python shell, and the notebook format spread well beyond Python. The name comes from Julia, Python, and R, the three languages it first supported.

It became the default tool for analysis for a plain reason. Analysis is iterative and mostly discarded. Most of what you type while exploring is a question you will never ask again, and a tool that makes throwaway questions cheap suits that work better than one built to run a finished program correctly.

## Do this with your first notebook

Open one and run a small experiment deliberately.

Put an import in the first cell, a value in the second, and something using that value in the third. Run them in order. Then delete the second cell and run the third again.

It still works, because the kernel remembers. Now restart the kernel and run everything from the top. It breaks.

Seeing that once, at a moment when nothing is at stake, will save you an afternoon later. Everything else about notebooks is convenience. This is the part that produces real mistakes.
