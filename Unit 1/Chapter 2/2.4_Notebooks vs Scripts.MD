## Notebooks are for finding out, scripts are for repeating

Your notebook is now sixty cells long. It loads three files, fixes a date column, and produces a table your team looks at. Someone asks whether it can run every Monday morning.

This is the moment the tool has to change. Everything making a notebook good for exploration works against it here. Cells can run in any order, results depend on what is in memory, and the whole thing assumes a human sitting in front of it pressing keys.

A script is the opposite. It runs top to bottom, in one order, with no memory of anything before it started, which is exactly what you want when nobody is watching.

## Which one fits the job

| What you are doing | Reach for |
| ----------------------------------------------- | --------- |
| Seeing what is inside a new dataset | Notebook |
| Trying five ways to fix a messy column | Notebook |
| Explaining a finding to a colleague | Notebook |
| Running the same steps every week | Script |
| Code that other code will use | Script |
| Anything that must run without a person present | Script |

The pattern down that table is consistent. Notebooks suit work done once and thrown away, and work whose purpose is to be read by a human. Scripts suit work that repeats.

## The three places notebooks hurt

Version control comes first. A `.ipynb` file is JSON containing your code, your text, and the stored output of every cell. Change one number and the file difference can run to hundreds of lines, most of it output nobody wants to review. Two people editing the same notebook produce merge conflicts that are miserable to resolve by hand.

Reuse comes second. A function written in cell 34 is stuck there. Nothing else can import it, so the usual response is copying it into the next notebook, and now two copies exist and drift apart.

Testing comes third. Automated tests import code and check what it returns. There is nothing to import from a notebook, so the code producing your most important numbers is the code nobody tests.

> A notebook is a record of thinking. A script is a piece of machinery. Confusing the two makes both worse.

## The arrangement most working analysts use

You do not have to choose once and for all. The common pattern moves code across as it stabilises.

Explore in a notebook. When a piece stops changing, and especially when you catch yourself copying it into a second notebook, move it into a `.py` file beside your notebook and import it:

```python
# cleaning.py, in the same folder
def standardise_dates(frame, column):
    """Parse the date column the way this project needs it."""
    ...
```

```python
# in the notebook
from cleaning import standardise_dates
```

The notebook keeps the narrative and the charts. The file keeps the logic that has earned permanence. Both get shorter.

One wrinkle: the notebook will not see your edits to `cleaning.py` after the first import, because the kernel caches imported modules. Restart the kernel after editing the file, or add the autoreload magic at the top of your notebook and let it handle this for you:

```python
%load_ext autoreload
%autoreload 2
```

None of this is where you start. A beginner who builds a tidy module structure before understanding the data has organised a guess. Explore messily first, extract only what has proved stable.

## Converting a notebook when the time comes

Jupyter can export a notebook to a plain script:

```
jupyter nbconvert --to script analysis.ipynb
```

Treat the result as a first draft rather than a finished script. The export carries across everything, including the cells where you looked at something once and the cells that failed. A script destined to run unattended needs the dead ends removed, the file paths made explicit rather than assumed, and a clear top-to-bottom order that the notebook never had to enforce.

## The three stages a piece of analysis passes through

| Stage | Lives as | Read by | Runs |
| ---------- | ------------------ | -------------------- | -------------------- |
| Exploration | Notebook | You | When you press keys |
| Explanation | Notebook, cleaned up | Your team | Once, on demand |
| Production | Script or module | Whoever maintains it | On a schedule |

Most student work never leaves the first stage, and that is appropriate. Most professional work that matters ends up in the third, and the transition is usually done badly because nobody decided when it should happen.

## When to move a notebook out

Three signals, and any one of them is enough.

You have copied a block of code into a second notebook. Someone other than you needs the output on a schedule. Or the notebook has grown long enough that you scroll to find things rather than remembering where they are.

Until one of those appears, stay in the notebook. Exploration forced into clean module structure too early usually stops being exploration.

Try the conversion once on something you have already written. Export a notebook to a script, run it from the terminal, and count how many things break. The number is usually higher than expected, and every one of them is a hidden assumption your notebook was quietly carrying.
