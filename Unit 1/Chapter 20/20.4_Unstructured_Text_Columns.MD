## Getting something countable out of free text

A column of customer complaints, review comments, or support tickets holds real information and nothing you can group, average, or plot.

```python
raw = pd.Series(["Delivered late, packaging damaged",
                 "delivered on time",
                 "DELAYED: courier issue #4482",
                 "Item missing from box, refund requested"])
```

The task is to derive columns from it. Not to understand the language, which is a different field, but to extract features an analysis can use.

## Simple features first

```python
raw.str.len()                    # [33, 17, 28, 39]
raw.str.split().str.len()        # [4, 3, 4, 6]
```

Length in characters and in words, in two lines.

These are more useful than they look. Complaint length often correlates with severity, review length with how strongly someone feels, and a sudden change in average length can mean a form changed or a bot started posting.

## Flags from keywords

```python
raw.str.contains('deliver', case=False)      # [True, True, False, False]
```

A boolean column marking whether a term appears. Once you have several of these, the free text becomes a small table of categories that grouping and cross-tabulation can work on.

```python
for term in ['delay', 'damage', 'refund', 'missing']:
    df[f'has_{term}'] = df['comment'].str.contains(term, case=False, na=False)
```

The `na=False` matters. Without it, missing comments produce missing values rather than False, and every subsequent filter silently drops those rows.

Case insensitivity matters too, as the example shows: `DELAYED` and `delivered` differ only in case from what a naive search would match.

## Extracting structure

```python
raw.str.extract(r'#(\d+)')      # [nan, nan, '4482', nan]
```

Where the text contains a structured element such as a ticket number, an order ID, a date, or an amount, a regular expression pulls it into its own column.

This is where the highest-value information usually is. A ticket number links the comment to another system; an amount makes the complaint quantifiable.

## Word frequency

```python
words = ' '.join(raw).lower().replace(',', '').split()
pd.Series(words).value_counts().head(5)
```

```
{'delivered': 2, 'late': 1, 'packaging': 1, 'damaged': 1, 'on': 1}
```

Counting words is the crudest possible summary and it identifies the vocabulary worth building flags from.

Two refinements are needed on real data. Common words such as "the", "and", and "on" dominate any count and are usually removed as stop words. And counting pairs of words rather than single ones catches phrases: "not delivered" means the opposite of "delivered".

## Cleaning before counting

Text needs the same standardisation as any category column, for the same reason.

```python
clean = (raw.str.lower()
            .str.replace(r'[^\w\s]', ' ', regex=True)
            .str.split()
            .str.join(' '))
```

Lowercasing, removing punctuation, and normalising whitespace. Without it, `damaged.` and `damaged` are different words and every count is split.

> Every technique in this topic compares text exactly. Case, punctuation, and spacing decide the result, and cleaning them is not optional.

## What to build, in order

| Step | Produces |
| -------------------------- | ------------------------------- |
| Length and word count | Two numeric columns |
| Presence of key terms | Boolean columns you can group by |
| Extracted identifiers | A join key to other data |
| Word and phrase frequencies | The vocabulary for better flags |
| Category assignment by rules | A single categorical column |

Work down that list only as far as your question requires. A question about whether delayed deliveries generate longer complaints needs the first two steps and nothing else.

## Where this stops

Everything above is pattern matching. It does not understand meaning, so sarcasm, negation, and context defeat it: "not damaged at all" matches a `damage` flag.

Sentiment analysis, topic modelling, and language models handle those, at the cost of being harder to check. A rule you wrote can be inspected and corrected; a model's judgement usually cannot, and for an exploratory analysis that transparency is worth a good deal.

Start with rules, measure how often they are wrong on a sample you read yourself, and escalate only if the error rate matters.

## Practise the derivation

Take any free-text column, or write forty short comments yourself.

Derive five columns from it: length, word count, two keyword flags, and one extracted pattern.

Then read fifty rows and check your flags by hand. The proportion your rules get wrong is the number that decides whether the rules are good enough, and it is a number almost nobody computes.
