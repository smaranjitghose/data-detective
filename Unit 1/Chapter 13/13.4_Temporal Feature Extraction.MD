## Pulling the useful parts out of a date

A date column holds more than a point in time. It holds a year, a month, a weekday, a quarter, a position in a sequence, and a distance from any other date, and every one of those can be the thing your analysis actually needs.

None of it is available until the column is a datetime rather than text.

```python
import pandas as pd
a = pd.read_csv('aapl.csv', parse_dates=['Date'])
a['Date'].dtype
```

```
datetime64[us]
```

The file holds 506 daily records of Apple's share price, from 2015-02-17 to 2017-02-16.

## The dt accessor

Once a column is a datetime, `.dt` gives every component.

```python
a['year']  = a['Date'].dt.year
a['month'] = a['Date'].dt.month
a['dow']   = a['Date'].dt.day_name()
a['q']     = a['Date'].dt.quarter
```

```
        Date  year  month        dow  q
0 2015-02-17  2015      2    Tuesday  1
1 2015-02-18  2015      2  Wednesday  1
2 2015-02-19  2015      2   Thursday  1
```

| Attribute | Gives |
| ----------------- | ------------------------------------ |
| `.dt.year`, `.dt.month`, `.dt.day` | The numeric parts |
| `.dt.dayofweek` | 0 for Monday through 6 for Sunday |
| `.dt.day_name()`, `.dt.month_name()` | The names as text |
| `.dt.quarter` | 1 to 4 |
| `.dt.is_month_end` | True on the last day of a month |
| `.dt.days_in_month` | Useful for per-day rates |

## What the components reveal

```python
a['dow'].value_counts()
```

```
Tuesday      105
Wednesday    105
Thursday     103
Friday        99
Monday        94
```

No Saturday or Sunday at all, which confirms this is trading-day data rather than calendar-day data. Monday is lightest, which is where public holidays fall most often.

That check takes one line and it tells you the shape of the calendar underneath your data. A dataset that should have weekend rows and does not has either a filter you did not know about or a business that closes.

```python
a['Date'].dt.is_month_end.sum()      # 17
```

Seventeen month-ends across two years, rather than 24, because month-ends falling on a weekend are absent. Anyone computing a month-end summary from this file needs to know that.

## Grouping by a time component

```python
a.groupby([a['Date'].dt.year, a['Date'].dt.quarter])['AAPL.Close'].mean().round(2)
```

```
2015  1    127.05
      2    127.94
      3    117.30
      4    114.30
2016  1     99.66
      2     99.40
      3    105.87
      4    113.40
2017  1    124.23
```

Nine quarters of average closing price, from a column that originally held only dates. The extracted components are what make this possible.

Group by year and quarter together rather than by quarter alone. Grouping by quarter alone would average the first quarter of 2015, 2016, and 2017 into one number, which is a different question and rarely the one intended.

## Differences between dates

```python
(a['Date'] - a['Date'].min()).dt.days.head(3)      # [0, 1, 2]
```

Subtracting two datetimes gives a duration, and `.dt.days` converts it to a number.

This is how you build features like days since signup, age at the time of an event, or the gap between an order and its delivery. The duration itself is rarely what you want; the number of days usually is.

## Resampling, when the date is the index

```python
a.set_index('Date')['AAPL.Close'].resample('ME').mean().round(2).head(4)
```

```
2015-02-28    129.70
2015-03-31    125.97
2015-04-30    127.29
2015-05-31    128.76
```

`resample` regroups a time-indexed series onto a regular frequency: `D` for daily, `W` weekly, `ME` for month end, `QE` quarterly, `YE` yearly.

It differs from `groupby` on an extracted month in one important way. Resampling produces a row for every period in the range, including periods with no data, which is what you want when a gap is meaningful. Grouping produces rows only for periods that appear.

## Two cautions

Time zones are absent from this data and present in most logs. A timestamp without a stated zone is ambiguous, and grouping by day gives different answers in different zones. When your data crosses zones, convert to one explicitly.

And the day-first problem from the cleaning unit applies to every date column you parse. `01/02/2023` is valid under both readings, and getting it wrong shifts rows by months while producing perfectly valid dates.

> Every date column needs two checks after parsing: the minimum and maximum, to confirm the range is plausible, and a count by weekday or by month, to confirm the calendar underneath is the one you assumed.

## Practise on a dataset with timestamps

Find any file with a date column, parse it, and extract year, month, weekday, and quarter.

Then run the weekday count. Whatever the data, that single table tells you whether you are looking at business days, calendar days, or something with a gap nobody mentioned.

Then compute a difference in days from the earliest date and check that the maximum matches the range you expect. If it does not, you have a parsing problem rather than a data problem.
