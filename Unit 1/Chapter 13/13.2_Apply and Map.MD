## Applying your own logic, and the cost of doing so

Some transformations have no built-in operator. A grading rule with four bands, a category derived from two columns, a lookup from an abbreviation to a full name.

pandas offers `map` and `apply` for these, and both come with a warning worth reading before the syntax.

## map, for element-by-element substitution

```python
import pandas as pd
df = pd.read_csv('penguins.csv')

df['species'].map({'Adelie': 'A', 'Chinstrap': 'C', 'Gentoo': 'G'}).head(3)
```

```
['A', 'A', 'A']
```

`map` works on a Series and takes either a dictionary or a function. With a dictionary it is a lookup table, which is the standard way to recode categories, expand abbreviations, or attach a label to a code.

The behaviour with an incomplete dictionary is the thing to know:

```python
df['species'].map({'Adelie': 'A'}).value_counts(dropna=False)
```

```
NaN    192
A      152
```

Every value not in the dictionary became missing. Silently, and 192 rows at once.

That is occasionally what you want and usually not. Check the missing count after any `map` with a dictionary, or use `.replace()` instead, which leaves unmatched values alone.

## apply, for a function per row or per value

```python
df['body_mass_g'].apply(lambda x: 'heavy' if x > 5000 else 'light').value_counts()
```

```
light    283
heavy     61
```

On a Series, `apply` calls your function once per value. On a DataFrame with `axis=1` it calls it once per row, and the function receives the whole row:

```python
def size_class(row):
    if pd.isna(row['body_mass_g']):
        return 'unknown'
    return 'large' if row['body_mass_g'] > 5000 else 'small'

df.apply(size_class, axis=1).value_counts()
```

```
small      281
large       61
unknown      2
```

Note that the row-wise version caught the two birds with no recorded mass, while the Series version put them in `light` because a comparison against a missing value returns False.

That difference is not about `apply`. It is about your function handling missing values, and it is the kind of thing that silently miscounts if you do not check.

## What it costs

On 344,000 rows, doing the same division two ways:

| Method | Time |
| ------------------------ | -------: |
| `col.apply(lambda x: x/1000)` | 63.8 ms |
| `col / 1000` | 0.34 ms |

A factor of 186. Row-wise `apply` is worse still: on 20,000 rows it took 74 ms against 0.87 ms for the vectorised form, a factor of 85.

The reason is the one from the NumPy unit. `apply` calls a Python function once per row, so the interpreter overhead you avoided by using arrays comes straight back.

> `apply` is a loop wearing a method's clothing. It is the right tool when nothing vectorised exists, and the wrong one when something does.

## The alternatives worth knowing first

Before reaching for `apply`, check whether one of these covers the case.

| Instead of | Use |
| ------------------------------------- | ------------------------------- |
| `apply` with an if-else | `np.where(cond, a, b)` |
| `apply` with several conditions | `np.select([c1, c2], [a, b], default=c)` |
| `apply` doing arithmetic | The arithmetic directly |
| `apply` doing string work | The `.str` accessor |
| `apply` looking up a dictionary | `map` or `replace` |
| `apply(axis=1)` combining two columns | Arithmetic on the two columns |

```python
np.where(df['body_mass_g'] > 5000, 'heavy', 'light')
```

Same result as the first `apply` example, and far faster.

The last row of that table is the one that matters most. Almost every `apply(axis=1)` written by a beginner is combining two or three columns in a way that vectorises directly.

## When apply is the right answer

Three situations.

The logic is complicated enough that expressing it as conditions would be unreadable, and the data is small enough that speed does not matter.

The function calls something external, such as a geocoding service or a parser, which cannot be vectorised at all.

Or the result depends on the row as a whole in a way that no combination of column operations captures.

In the first case, be honest about the size threshold. On a few thousand rows, `apply` finishing in 50 milliseconds instead of 1 costs you nothing. On several million it is the difference between a working notebook and one you abandon.

## Practise the replacement

Find or write three `apply` calls: one doing arithmetic, one doing an if-else, and one doing string manipulation.

Replace each with a vectorised equivalent and confirm the results match with `.equals()`.

Then time both versions on a table you have duplicated to a million rows. The ratio you measure is the one that decides whether this habit matters in your work.
